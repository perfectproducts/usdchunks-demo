usd_chunks · the procedural layer for OpenUSD

How USDChunks works

A USD file records what a scene is. USDChunks also records how it was made: a node network of small Python "chunks", stored as ordinary prims in the same .usda. Open the file and the steps are still there to change and cook again.

Plain USDWhat the scene is

Meshes, transforms, materials, instancers. Every USD tool reads it. Once baked, nothing records which steps produced it.

USDChunks addsHow the scene was made

A graph of steps (reference this, scatter that, bind a material) whose results are composed on top of the scene. Change a step and the result follows.

Try it: a procedural ladder

Three numbers drive this network: length, width and rung spacing. Everything else is worked out from them by expressions inside the network: where the rails stand, how many rungs fit and how high each one sits. Every command below was run on this machine. The files are in C:\_DEMO\USDChunks\tutorial.

GapRiseRailBoxRailsRailPairRungBoxRungStepsDropRailDropRung

Outlined nodes hold the three drivers: Rails.sy is the length, Rung.sx the width and Rung.ty the rung spacing. Dashed nodes are small maths helpers.

  1. Open a shell with USD and USDChunks on the path. 
    call C:\_DEMO\USDChunks\env.bat
  2. Build the parts. A rail is a 1 m cube squashed into a thin post, then copied once to make two. A rung is a second cube squashed into a bar, then copied up the ladder. Each scene.create.… call adds one chunk, and passing the previous chunk wires it in. 
    from usd_chunks import Scene

with Scene.new() as scene:
    gap  = scene.create.vector_math_ops(operation="Scale", a=(1, 0, 0), name="Gap")
    rise = scene.create.vector_math_ops(gap, operation="Scale", a=(0, 1, 0), name="Rise")

    rail  = scene.create.usd_cube(rise, prim_path="/World/ladder/rail", name="RailBox")
    rails = scene.create.transform(rail, primpath_location="/World/ladder/rail", name="Rails",
                                   sx=0.06, sy=3.0, sz=0.06)          # sy = LENGTH
    pair  = scene.create.duplicate_prim(rails, source_prim="/World/ladder/rail",
                                        dest_path="/World/ladder/rails", copies=2, name="RailPair")

    rung   = scene.create.usd_cube(pair, prim_path="/World/ladder/rung", name="RungBox")
    rung_x = scene.create.transform(rung, primpath_location="/World/ladder/rung", name="Rung",
                                    sx=0.5, sy=0.04, sz=0.05, ty=0.3) # sx = WIDTH, ty = SPACING
    steps  = scene.create.duplicate_prim(rung_x, source_prim="/World/ladder/rung",
                                         dest_path="/World/ladder/rungs", name="Steps")

    tidy = scene.create.prune_prim(steps, prim_path="/World/ladder/rail", name="DropRail")
    tidy = scene.create.prune_prim(tidy,  prim_path="/World/ladder/rung", name="DropRung")
    scene.set_output(tidy)
    The two Prune chunks remove the original rail and rung, so only the copies are left.
  3. Write the rules. An @Node.param@ expression makes one value follow another. These seven lines are what make the ladder procedural: 
        gap.get_param("scale").value  = "@Rung.sx@"               # Gap  = (width, 0, 0)
    rise.get_param("scale").value = "@Rung.ty@"               # Rise = (0, spacing, 0)
    rails.get_param("ty").value   = "@Rails.sy@ / 2"          # rails stand on the floor
    rails.get_param("tx").value   = "-@Rung.sx@ / 2"          # left rail at the left edge
    pair.get_param("copy_translate").value  = "@Gap.result@"  # right rail one width over
    steps.get_param("copies").value = "(@Rails.sy@ - 0.05) / @Rung.ty@"   # rungs that fit
    steps.get_param("copy_translate").value = "@Rise.result@" # each one spacing higher

    scene.save("ladder_network.usda")   # the network: 10 chunks with their expressions
    scene.export("ladder.usda")         # the result: plain USD cubes
    copies is a whole number, so the division is rounded down: (3 − 0.05) / 0.3 = 9.8 gives 9 rungs. A Translate value is a vector, and an expression can only fill a vector as a whole. That is why Gap and Rise exist: each turns one number into a vector.
  4. Run it. python ladder.py writes ladder_network.usda, the network, and ladder.usda, which holds two rails and nine rungs as ordinary Cube prims that any USD tool can open.
  5. Make variants without touching code. Cook the saved network again with different drivers. The command line takes the same Node.param=value names: 
    python -m usd_chunks.cli run ladder_network.usda Rails.sy=2                         -o ladder_short.usda
python -m usd_chunks.cli run ladder_network.usda Rails.sy=5 Rung.sx=0.8 Rung.ty=0.5 -o ladder_tall_wide.usda
python -m usd_chunks.cli run ladder_network.usda Rung.ty=0.15                       -o ladder_dense.usda
    That gives 6, 9 and 19 rungs. The rails move out to ±0.4 m when the width is 0.8. These are the ladders in the render above.
  6. Open it live. usdview_chunks.bat tutorial\ladder_network.usda opens the network with the Chunks panel. Change Rung's ty (the spacing) and the network cooks again, so rungs appear or disappear to fill the length.

A node is a prim, a wire is a connection

        What it cooks into its own layer


        

      

    

  

  
Each node is a Chunk prim under /chunks. Its params are inputs: attributes, and info:chunkType names the Python module that runs it. The execution wire is an ordinary USD connection on inputs:chunk. An expression is stored as text in the param's customData plus a USD connection to every param it reads (shown here as (expression = …) for short). Because it is all text USD, a network diffs cleanly in git and any USD tool can open it.






  
A chunk is one short Python module

  


from usd_chunks import chunk

def main():                       # the node and its params
    node = chunk.Chunk("Reference")
    node.add_param(chunk.FileBrowser("file_path"))
    node.add_param(chunk.LineEdit("primpath_location",
                   default_value="/Asset"))
    return node

def execute(node):                # cook into own layer
    path = node.get_param("file_path").value
    if path:
        prim = node.get_stage().DefinePrim(
            node.get_param("primpath_location").value, "Xform")
        prim.GetReferences().AddReference(path)

def config():                     # what the chunk is
    return chunk.DefaultConfig(
        category=chunk.StandardCategory.USD,
        description="Brings a USD file in as a reference.")

    

      
main()Builds the node: sliders, menus, file pickers and lists. USDChunks generates the panel, the graph node and the command-line parameters from it, so you write no Qt or plugin code.

      
execute(node)Runs on every cook, starting from an empty layer each time. It must be deterministic: the same inputs give the same layer.

      
config()Metadata: its Tab-menu category, a description that people and AI agents read, pip requirements, which hosts it supports, and caching.

      
commit(node)Optional. Runs once after the whole graph has cooked, for chunks that write files to disk, such as Export USD or Render.

    

  

  
Chunks are discovered from the folders on USD_CHUNK_DIRS, plus the roughly 100 bundled ones. Python is used because every USD host already embeds it. Heavy work goes to compiled code: USD's C++, numpy, MuJoCo.






  
What happens when the graph cooks

  

    
  

  
    
    
  1. Choose what to cook. The graph cooks toward its Output, or toward the active View while you work. Only chunks upstream of it run. Anything not wired in stays idle.
    2. 
    
  2. Cook upstream first. Each chunk sees a stage made of the scene plus the layers of the chunks before it. That is how Steps can copy the rung that RungBox made and Rung scaled, and how Rise's result is ready when Steps reads it.
    3. 
    
  3. Run execute() into an empty layer. The chunk's layer is rebuilt from scratch, so results never pile up across cooks.
    4. 
    
  4. Apply only the difference. USDChunks compares the new layer with the previous one and changes only what differs, so the viewport updates a value instead of rebuilding the prim.
    5. 
    
  5. Reuse what has not changed. A slow chunk can cache its layer by its inputs. When you reopen a saved network, each chunk can load its stored result instead of cooking again.
    6. 
    
  6. Commit. After everything has cooked, chunks with commit() write their files. usdchunks run and Scene.commit() trigger this. In usdview, Export USD has a button for it.
    7. 
  

  
Because every result sits in the session layer above your own layers, the source scene is never modified. To change a result, change a chunk's params (which can also be overridden from any layer) or add a chunk after it. An Edit Target chunk is the exception: it sends its branch's edits into a named layer instead, which is how the department example writes layout.usda, lighting.usda and camera.usda.






  
Two kinds of wires

  

    

      
Execution wire: what cooks after what

      
It connects one chunk's outputs:chunk to the next one's inputs:chunk. This defines the chain, the cook order and the layer order.


token inputs:chunk.connect =
    </chunks/…/Rung.outputs:chunk>

      
The Merge, Switch and Dot chunks join, choose between and fan out branches.

    

    

      
Value link: one param reads another

      
An expression in a param's value, stored together with a USD connection. Change the source and every linked param updates.


float  inputs:translate_grp:ty  = "@Rails.sy@ / 2"
int    inputs:copies_grp:copies = "(@Rails.sy@ - 0.05) / @Rung.ty@"
float3 inputs:copies_grp:copy_translate = "@Rise.result@"

      
From Python, passing node.get_param("prim_path") as a value creates the link.

    

  






  
Networks become assets

  

    

      
A ChunkGroup is a subnet: chunks nested under one prim, with its own Output. Saved as a file, it becomes a reusable asset.

      
Lofting exposes chosen inner params on the group node, for example Scatter_density or Stairs_copies. Whoever uses the group sets only those.

      
A group is loaded through ordinary USD composition (reference, payload or sublayer). Its chunks show as locked, and any param you change is written as an over in your own layer, so the shared file stays untouched.

    


# scene that uses a group asset
scene.create.reference(
    last,
    file_path="groups/spiral_stairs.usda",
    name="Stairs",
    Stairs_copies=12,                    # lofted
    Stairs_copy_rotate=(0, -30, 0),      # lofted
    Stairs_dest_path="/World/stairs",
)

# or override from the command line
usdchunks run groups_network.usda \
    Stairs.Stairs_copies=20 -o out.usda

  






  
One file, every host

  
The network lives in USD, so any program that embeds USD and Python can open it as a graph or cook it without a UI.

  

    
usdviewA USD plugin (PXR_PLUGINPATH_NAME) adds a Chunks panel and menu. Press Tab to add chunks.

    
HoudiniEach chunk is a LOP node in Solaris, with ordinary Houdini parms and wires (Houdini 21).

    
BlenderAn add-on with a USDChunks editor and its own viewport handles.

    
Command lineusdchunks run cooks to the Output with param overrides. batch runs it once per file that a glob matches.

    
PythonScene.new() and scene.create.<chunk>() build or edit a network that then opens as a graph.

    
Other front endsStandalone Flet and Dear ImGui graph editors. Viewport handles come from the separate usd_gizmos repo.

  






  
Worth knowing

  

    
Alpha. The core works, but the APIs still change between releases. The project does not recommend it for production yet.

    
Opening a network runs code. A .usda file can't install chunks, but opening one runs the chunks you have installed, using the values saved in the file. Some chunks, such as the Python script chunk, run code stored in the file. Treat networks from others like any script.

    
Built to be read by agents too. Every chunk describes itself in config(), and the repository ships an AGENTS.md and skills, so an AI agent can build networks through the same Scene API a person uses.
